# eval-driven-improvement

## 언제 쓰는가

버그·실패·오동작을 발견했을 때. 그리고 같은 실패가 두 번째로 보일 때는 반드시.

## 프로세스

1. 실패를 최소 재현으로 줄인다 — 입력, 기대, 실제.
2. 분류한다:
   - **코드가 틀렸다** → 고치고, 재현을 `tests/`에 남긴다. 반복된 실패면
     `tests/regression/`.
   - **에이전트 판단이 틀렸다** (잘못된 파일 수정, 지시 오해, 잘못된 도구 경로)
     → `evals/regression/`에 케이스로 남긴다.
   - **수용 기준이 틀렸다** → 고치지 않는다. 사람에게 보고한다.
3. 고친 뒤 `scripts/gate_chain.sh`로 회귀 전체를 돌린다.
4. 회귀 층이 100%에서 떨어져 있으면 새 작업을 시작하지 않는다 — 회귀 복구가
   먼저다.

## 입력과 출력

- 입력: 실패 관찰.
- 출력: 최소 재현 + 분류 + 회귀 케이스(반복 시) + 통과하는 게이트.

## 경고 신호 (red flags)

- 실패를 고쳤는데 재현이 어느 테스트에도 남지 않았다.
- 같은 실패를 두 번째 고치고 있는데 회귀 케이스가 없다.
- 커버리지 수치를 올리는 것이 목표가 되어 있다 — 커버리지는 단서지 목표가
  아니다.

## 검증

- 고침 커밋에 재현 테스트가 함께 있는가.
- `tests/regression/`과 `evals/regression/`이 전부 통과하는가.

## 거부할 흔한 합리화

- "급하니 고치기만 하고 테스트는 나중에" — 나중은 오지 않는다는 것이 회귀
  층이 존재하는 이유다.
- "테스트를 조금 고치면 통과한다" — 실패를 지우는 것과 고치는 것은 다르다.
  수용 테스트라면 봉인 위반이다.
- "flaky니까 다시 돌리면 된다" — 재실행은 판정을 미룰 뿐이다. 원인 분류
  없는 재시도는 실패를 신호에서 소음으로 바꾼다.
