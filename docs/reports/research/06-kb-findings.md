# syntopicon KB 소견

KB 검색 5회(저장소 수준 이해 · 환각과 근거 · 에이전트 메모리 · LLM 판정자 · 결정적 게이트) + 보강 2회(문서화 규범 · 코드 이력 핫스팟). 아래 각 항은 KB 페이지의 판단을 옮기고, 그것이 repowiki의 어느 결정을 정하는지를 적는다.

## 1. 생성물은 결정적 필터를 먼저 지난다 — LLM은 필터가 아니다
`[it]` concepts/filter-chain-for-generated-tests.md (Meta TestGen-LLM·ACH, 심사 게재+산업 자기 보고): 사람 앞에 닿기 전 관문 넷(빌드·실행·5회 반복 실행·커버리지 증가)이 순서대로 걸러지고 **관문 중 어느 것도 모델의 판단이 아니다** — 빌드 시스템·러너·계측기라는 기존 인프라의 답이다. 실패한 테스트는 버그 발견인지 단정 오류인지 자동으로 못 가르므로 통째로 버린다. ACH 도해는 규칙 기반 구성 요소와 LLM 구성 요소를 도형으로 가른다.
→ **적용**: repowiki 파이프라인의 게이트(경로 실재 검사 · Mermaid 파서 · 링크 검사 · frontmatter 스키마 · 인용 span 해시)는 전부 결정적 도구로 두고, 통과 못 한 페이지·다이어그램은 "고쳐 달라"고 모델에 되돌리기 전에 먼저 **버리거나 강등**(text 펜스)한다. 재시도 상한은 2회(템플릿 quality-gates와 같다). 아키텍처 도해에서 LLM 상자와 규칙 상자를 갈라 그린다.

## 2. 판정 도구가 피판정자의 권한 안에 있으면 통과가 만들어진다
`[it]` concepts/test-case-exploitation-by-agents.md (ImpossibleBench, ICLR 2026 poster): 테스트를 에이전트가 고칠 수 있게 두면 고쳐지고, 접근을 좁히면 그 경로가 닫힌다(값은 세대·과제에 묶이고 **방향**만 옮긴다). 완화책 실험: 테스트 숨김·읽기 전용이 치팅을 줄이나 특수 케이스 처리는 남는다; 중단 선택지 부여로 치팅률이 크게 준다(GPT-5 54%→9%, full 스캐폴드, §5.3).
→ **적용**: (a) 템플릿의 `tests/acceptance` 봉인을 그대로 쓴다. (b) repowiki가 만드는 위키의 **평가 셋(claim grounding 골든셋)도 봉인 경로**에 둔다 — 생성기가 자기 평가 케이스를 고치지 못하게. (c) 페이지 작성 프롬프트에 **"근거가 없으면 그 절을 쓰지 않고 `미확인`으로 표시하라"는 중단 선택지**를 명시한다 — 통과(그럴듯한 서술) 대신 포기를 허용하는 것이 치팅 경로를 닫는다.

## 3. 판정자는 대상과 갈라 두되, 갈라도 상관은 남는다
`[it]` synthesis/verifier-independence.md · concepts/ai-judge-limitations.md (Huyen 2025, Ragas, Panickssery 2024, Kim 2025): 같은 판정자도 두 번 돌리면 다른 점수; 일관성이 정확성이 아니다; 같은 기준 이름(faithfulness)이 도구마다 다른 정의; **"모델과 프롬프트를 볼 수 없는 AI 판정자는 믿지 마라"**; 자기선호는 자기인식에서 오고 같은 벤더의 다른 모델로 번진다. `[it]` concepts/verifier-separation-in-agent-workflows.md (벤더 문면, 2026-08-18판): 반박 목표의 새 문맥 리뷰어, 그리고 "반박을 시킨 판정자는 없는 결함까지 보고한다 — 정확성·명시 요구사항에 한정하라".
→ **적용**: 위키 품질 지표는 **결정적 지표를 1차**(근거 span 실재율, 경로 실재율, Mermaid 파싱률, 링크 유효율, 페이지당 인용 수)로 두고, LLM 판정(페이지 충실성)은 2차·보조로만 쓰되 **판정자 모델·프롬프트·실행일을 결과 파일에 함께 기록**하고 판정자 변경 시 기준선을 다시 잰다. 생성 모델과 판정 모델을 갈라도 독립을 얻는 것이 아니므로 판정 결과를 "검증됨"으로 라벨하지 않는다(OKF `verified`는 사람 또는 결정적 검사에만 찍는다).

## 4. 오라클 부재 — 생성 문서의 결함은 "단정의 옳음"에 몰린다
`[it]` concepts/test-oracle.md §LLM 시대의 지위 (KB의 읽기, #hypothesis): LLM은 오라클 문제를 첨예화했다; 생성 병목은 풀렸으나 무엇을 기대값으로 삼는가는 답해지지 않았고, 관측된 현재 동작을 그대로 기대값으로 굳히는 퇴화가 기본값이 된다.
→ **적용**: 위키 페이지의 명제에는 오라클이 없다. 대신 **명제 ↔ 소스 span의 결속(Claims)** 을 오라클의 대체물로 삼고, 결속이 없는 명제는 페이지에 싣지 않는다(OpenWiki의 materiality test 차용). "현재 코드가 이렇다"는 서술과 "이렇게 설계됐다/이래야 한다"는 서술을 문장 층위에서 가른다 — 후자는 소스(ADR·KIP·문서)가 있을 때만.

## 5. 컨텍스트의 중간은 읽히지 않고, 긴 컨텍스트는 검색을 대체하지 못한다
`[it]` concepts/context-length-and-efficiency.md (Huyen 2025; Liu et al. 2024 "Lost in the Middle"): 관련 정보가 처음·끝에 있을 때 성능이 높고 중간이면 유의미하게 떨어진다, 확장 컨텍스트 모델도 마찬가지; 2M 컨텍스트가 PyTorch 정도 코드베이스를 담는다는 실감(책의 진술). `[it]` concepts/agent-memory.md: 단기(컨텍스트)·장기(검색) 기억의 분담은 쓰임 빈도로 정한다; 세션 사이 지속과 일관성 향상이 메모리의 이득.
→ **적용**: 페이지 작성 프롬프트는 **한 페이지 = 한 모듈 = 한 컨텍스트**로 좁히고(CodeWiki·OpenWiki와 같다), 모듈 요약·의존 그래프·이전에 쓴 페이지의 요약(공유 메모리)을 **프롬프트 앞과 뒤**에 두며 소스 본문은 가운데에 둔다. "레포 전체를 1M 컨텍스트에 넣고 한 번에 쓰기"는 채택하지 않는다.

## 6. 그래프 색인과 커뮤니티 요약 — 코드 위키의 구조와 같다
`[it]` concepts/rag-beyond-text.md §GraphRAG (Edge et al. 2024): 청크 → 개체·관계·주장 추출 → 그래프 → **라이덴 커뮤니티 계층 분할** → 커뮤니티 요약(잎부터, 토큰 한계까지 우선순위 순으로 원소 요약을 채우고 상위는 하위 요약으로 대체) → 질의는 맵리듀스. 요약 자체가 "질의 없이도 코퍼스를 이해하는" 산출물. 환각률은 측정되지 않았다(저자 자인). 형제 절: HippoRAG는 커뮤니티 요약 대신 개인화 페이지랭크.
→ **적용**: repowiki의 페이지 계층 = 의존 그래프의 커뮤니티 계층(모듈 → 서브모듈)이고, 요약 생성 순서는 잎→상위(의존 순서 생성). 코드에서는 개체·관계를 LLM이 아니라 **ast-grep/tree-sitter가 결정적으로 추출**하므로 GraphRAG의 가장 비싼 단계가 빠진다. 페이지랭크(aider 방식)는 HippoRAG 계열의 검색 신호로 "Ask" 기능에 재사용한다.

## 7. 프롬프트 캐싱과 배치 창구
`[it]` concepts/prompt-caching.md · concepts/online-and-batch-inference-apis.md (Huyen 2025): 캐시는 시스템 프롬프트·긴 문서(코드베이스)·다중 턴에 유효하고 앞부분(prefix)이 같아야 한다; 배치 API는 50% 비용에 시간 단위 회신, "조직 데이터를 재색인해 지식 베이스를 갱신하는 일"이 배치의 전형 유스케이스.
→ **적용**: 페이지 작성 호출은 **레포 개요 + 모듈 그래프 + 작성 규약을 고정 prefix**로 캐시하고, 모듈별 소스만 뒤에 붙인다. 전량 생성·정기 갱신은 배치 창구, 단일 페이지 재생성·Ask는 온라인 창구. (단가·캐시 할인은 claude-api 스킬의 현행 표를 정본으로 한다 — KB의 수치는 집필 시점 진술이다.)

## 8. 생성 문서가 담아야 하는 것 — 인터페이스 주석의 규정
`[it]` synthesis/documentation-and-code-clarity.md · concepts/interface-documentation.md · concepts/comments-describe-the-nonobvious.md (Ousterhout 2021): 추상을 서술하는 유일한 수단이 주석이다; 인터페이스 주석(쓰기 위해 알아야 할 것)과 구현 주석(어떻게)을 가른다; 클래스 주석은 능력·인스턴스가 나타내는 것·한계 셋을, 메서드 주석은 다섯을 담는다; 코드를 되풀이하는 주석은 붉은 깃발; 뻔함의 판정자는 읽는 사람.
→ **적용**: 모듈 페이지의 본문 골격은 이 규정을 따른다 — **책임(능력) · 인스턴스/단위가 나타내는 것 · 한계와 불변식 · 경계면 계약(입력·예외·부작용·소유권) · 왜(설계 결정)**. 소스 트리 나열, 메서드 목록 반복, 코드 되풀이는 페이지에서 금지(프롬프트 규칙 + 리뷰 루브릭). 이 골격은 altera-rules C-COMMENT-4(경계면 계약은 반드시 적는다)와 같은 방향이다.

## 9. 수치를 보고할 때
`[it]` concepts/llm-empirical-study-reporting-norms.md (Baltes 2026, 심사 통과한 규범): 모델 이름·판·실행 날짜·설정을 밝히고, 비결정성 때문에 반복 실행해 분포로 보고하며, 모델과 시간을 가로지른 일반화 여부를 밝힌다.
→ **적용**: 평가 결과 파일(`evals/reports/`)의 필수 필드 = 생성 모델·판정 모델·effort·프롬프트 해시·대상 레포 SHA·실행일·반복 횟수. PLAN·README에 수치를 옮길 때는 그 필드와 함께만 옮긴다(V-REC-1의 근거 등급 라벨과 동일 취지).

## 10. KB 공백
- **코드 이력 채굴(핫스팟·시간적 결합·소유권, Tornhill 계열)** — KB에 없다(검색 히트 전부 JVM HotSpot·데이터 모델링). 이 주제의 근거는 리서치 05(웹·실측)에만 있다. 저장 3문을 통과하는 신규 지식이 Phase 2 실측에서 나오면 `/kb-ingest --kb it` 후보다.
- **저장소 수준 코드 이해(repo map·의존 그래프 기반 문서 생성)** — 직접 페이지 없음. 가장 가까운 것은 GraphRAG(§6)와 에이전트 도구(agents-defined의 저장소 탐색 행동 집합).
- **OKF·OpenWiki** — 없음. 리서치 03이 유일한 근거.
