Hands-on re-evaluation · 2026-09-09 · same 300-page Korean sample wiki fed to four generators

Repowiki SSG Verdict

Criteria in the user's order: (1) reading UX for a diagram-heavy Korean architecture wiki, (2) air-gapped build as pass/fail, (3) maintenance/EOL. Added constraint: the built site must work when opened from file:// with no server (a strike if it needs python -m http.server, not a disqualification). GitLab Pages considerations were dropped per scope change.

Verdict
MkDocs Material 9.7.7 (offline plugin, self-hosted Mermaid, panzoom) — with Zensical as the same-content successor

The measurement that decides it is the file:// test, not air-gap cost. The previous conclusion ("MkDocs because air-gap") was wrong on its own terms: all four generators build with zero egress once dependencies are vendored (Fumadocs 10.4 s, Starlight 5.0 s, MkDocs 3.7 s, Zensical 2.3 s), and MkDocs actually needed the most workarounds to get there. What separates them is the deployment mode the user actually has: opened from the filesystem, MkDocs Material and Zensical work end-to-end (navigation, Mermaid, dark mode, search, 0 failed requests); Starlight needs a third-party plugin last released Dec 2024 and its Pagefind search is dead; Fumadocs does not work at all.

On reading UX alone, served over HTTP, Starlight wins (lightest pages at 324 KB vs 1,114 KB, Korean search that handles particles, 0 axe violations, clearest hierarchy) and Fumadocs has the best diagram handling (native-size SVG with horizontal scroll). If the S3 / static-server path becomes the primary deployment, the verdict flips to Starlight; switching cost is the frontmatter/sidebar emitter in the generator, which already exists in gen_wiki2.py.

The verdict carries an expiry date: Material is in its final maintenance window until 2026-11-05 (57 days). The identical docs/ tree built under Zensical 0.0.60 with the same UX and the same file:// pass, so the continuity path is verified, not assumed.

How the three criteria combine

  • UX in the deployment mode the user has (file://): Starlight's 42 collapses because search — its biggest lead — does not work there and links need an unmaintained plugin; Fumadocs' 35 collapses to nothing. MkDocs (32) and Zensical (30) keep their full score. That is the decisive measurement.
  • UX served over HTTP (S3 later): Starlight 42 > Fumadocs 35 > MkDocs 32 > Zensical 30. The diagram problem the user cares about most is a three-way tie at "shrunk to ~18–28 %, zoom required"; only Fumadocs renders at native size. MkDocs' zoom is a maintained plugin; the other two needed ~40 lines of custom code from me.
  • Air-gap: all pass; it never was a ranking axis, and MkDocs was the hardest to get through it.
  • Maintenance: MkDocs loses outright (EOL in 57 days), but the loss is bounded: a build-time tool with no server component, and the same docs/ tree builds under its successor today with identical results in both constraints.

2. What the runner-up would cost to switch to later

To Starlight (if served over HTTP)

  • Generator: emit Starlight frontmatter (sidebar.order, unquoted lastUpdated, tableOfContents:false on diagram pages), :::note[…] asides, absolute links, and an explicit sidebar.json — all already in gen_wiki2.py; MkDocs' ??? details become <details>.
  • Vendor: Node 22 (already in the image), npm-cache (~555 MB) with astro 7.3.1, @astrojs/starlight 0.42.0, astro-mermaid 2.1.0, mermaid 11.17.2, sharp.
  • Carry: the 30-line zoom overlay + 4 CSS rules (or accept shrunk diagrams); no breadcrumbs; expect a breaking minor roughly monthly and an Astro major every 12–15 months (once 3.5).
  • Do not expect file:// search; if that matters, this path is closed.

To Zensical (same content, when it matures)

  • Config only: zensical.toml with nav, font = false, extra_javascript Mermaid, extra.polyfills shim, [project.plugins.offline] — verified building the identical docs/ tree.
  • Lose until supported: privacy (irrelevant once fonts are off and Mermaid is self-hosted — output had zero external URLs), llmstxt, panzoom (untested; likely needs its markdown extension re-registered).
  • Gain: Rust build (2.3 s), maintained successor with the same team.

3. What each generator cannot do that matters for this purpose

MkDocs Material cannot

  • Widen a single page for a big diagram — there is no per-page full; the content column is 688 px at 1440 and 757 px at 1920 (global CSS override only).
  • Find Korean words carrying particles: 컴포넌트 and 퍼거토리 returned 0 hits although they occur on dozens of pages; lunr indexes whole tokens (a custom search.separator could split particles — untested).
  • Lazy-load Mermaid offline: its loader hard-codes unpkg, so the 3.4 MB library ships eagerly on all 300 pages (965 KB gz per page).
  • Expose the rendered SVG: Material renders into a closed shadow root, so page scripts/CSS cannot reach nodes (I had to monkey-patch attachShadow to measure it).
  • Offer per-page "copy as Markdown"; only site-level llms.txt files.
  • Receive any fix after 2026-11-05.

Fumadocs / Starlight cannot

  • Fumadocs: open from file:// at all; keep output small (217 MB for 300 pages; 243 KB HTML per page because the whole tree is serialised into each RSC payload); pass raw HTML through .md; resolve bare relative links (needs ./); pass axe contrast on muted text; run on anything but Next 16 / React 19.2; survive its single maintainer leaving.
  • Starlight: search from file:// (Pagefind fetches absolute paths); link relatively without a 2024 community plugin; show breadcrumbs; make a sidebar group label itself a link; render a 25-node graph at readable size (astro-mermaid pins max-width:100%; zoom is custom); keep a stable API across 0.x minors.
  • Both: ship without a Node toolchain in the build image (not a cost here) and without ~40 lines of bespoke zoom code for the diagrams this wiki is about.

Identical semantic content; only frontmatter, callout/details syntax and link form differ per target.
  • Configs: MkDocs mkdocs-file.yml (privacy + offline + llmstxt + panzoom, navigation.sections/indexes/path, toc.follow, pymdownx.details/superfences); Fumadocs .md pages, full: true, defaultOpenLevel: 1, clerk TOC, trailingSlash, OG-image route removed; Starlight explicit sidebar, astro-mermaid autoTheme, Pagefind default, lang="ko"; Zensical zensical.toml converted from the same nav.
  • Egress block: sandbox-exec profile denying network-outbound except loopback/unix sockets, plus HTTP(S)_PROXY=127.0.0.1:9. Verified: curl 1.1.1.1 fails, loopback connects.
  • Browser: puppeteer-core 25 on system Chrome; per load a fresh incognito context (Material persists the palette in localStorage, which leaked the light choice into the first dark run); prefers-color-scheme emulated; Mermaid readiness by DOM polling every 100 ms; transferred bytes from CDP Network.loadingFinished (server gzip); axe-core 4 (wcag2a/aa).
  • Search timing = ms from first keystroke to first visible result on a cold page.

5. Unverified or limited

  • Zensical was a quick check only: no panzoom, no breadcrumbs, no axe on file://; its search UI (shadow DOM) was verified by screenshot and text scrape, not by result-count selectors.
  • Starlight dark toggle under file://: my toggle test was inconclusive (page already dark from the emulated scheme); diagrams and links verified.
  • Pagefind's docs list Korean under "specialized languages" with segmentation but demonstrate only Chinese; the measured Korean hits show segmentation working in practice.
  • Material's search.separator as a Korean-particle mitigation is an idea, not tested.
  • Fumadocs Next 15→16 migration doc: not found; the v16 blog states the Next 16 / React 19.2 requirement directly.
  • "MkDocs unmaintained since August 2024" is squidfunk's statement; not independently verified.
