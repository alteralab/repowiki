# 게이트 실행 기록

여기 없는 게이트는 돌지 않은 게이트다. 새 게이트를 넣는 커밋은 위반·무위반
표본에서 발화한 기록을 여기 함께 남긴다.

## 동봉 게이트의 완주 실적 (템플릿 출하 시점)

| 게이트 | 표본 | 결과 |
|---|---|---|
| `hooks/seal_acceptance.py` | acceptance 경로 쓰기 | 차단 (exit 2, 사유 stderr) ✅ |
| 〃 | src 경로 쓰기 | 통과 ✅ |
| 〃 | acceptance + `ACCEPTANCE_UNSEAL=1` | 통과 ✅ |
| `seal_check.sh` | src+acceptance 혼합 스테이징 | 실패 (exit 1) ✅ |
| 〃 | acceptance 단독 | 통과 ✅ |
| 〃 | 혼합 + UNSEAL | 통과 ✅ |
| `transition_ledger.py` | 최초 기록 (fail 1, pass 1) | 기록 ✅ |
| 〃 | acceptance 변경 + fail→pass | **flag 1건** ✅ |
| 〃 | 변경 없음 + 결과 동일 | flag 없음 ✅ |
| `gate_chain.sh` 6단계 (evals) | 케이스 없음 | SKIP 표시 ✅ |
| 〃 | 케이스 있음 + 러너 없음 | 실패 (exit 1) ✅ |
| 〃 | `evals/run.sh` 존재 | 실행 ✅ |

봉인을 `sealed_paths.txt` 단일 원천으로 개정한 뒤 재완주:

| 게이트 | 표본 | 결과 |
|---|---|---|
| `hooks/seal_acceptance.py` (개정판) | 봉인 경로 쓰기 | 차단 (exit 2) ✅ |
| 〃 | 비봉인 경로 · UNSEAL | 통과 ✅ |
| 〃 | 봉인 목록 부재 | **차단 (exit 2)** — 조용한 통과 금지 ✅ |
| `seal_check.sh` (개정판) | 혼합 · 단독 · UNSEAL | 실패/통과/통과 ✅ |
| 〃 | 봉인 목록 부재 | 실패 (exit 1) ✅ |

도구 로컬화(uv.lock·npx) 및 tpl_init 도입 뒤:

| 게이트/도구 | 표본 | 결과 |
|---|---|---|
| `tpl_init.sh` | 심링크 2개 고의 파손 + 신규 복사본 | git init·이름 치환·심링크 복구·uv.lock 생성·훅 설치 ✅ |

`tpl_init`을 파이썬 CLI(`tpl_init.py`, argparse·stdlib 전용)로 교체한 뒤 재완주 —
복사 단계 내장(.git·자기 자신 제외), 구판 sh 삭제:

| 표본 | 결과 |
|---|---|
| --help · 인자 부족 · 잘못된 이름 · 비어 있지 않은 대상 · 비템플릿 루트 | 각각 0·2·1·1·1 종료, 사유 출력 ✅ |
| 정상 경로 | 자기 자신 미복사·템플릿 이력 0커밋·심링크 보존·이름 치환·uv.lock·훅 설치, 첫 커밋 봉인 통과, gate_chain 완주 ✅ |
| `seal_check.sh` | 인스턴스 첫 커밋(.gitkeep 포함 전체) | .gitkeep 면제로 통과 ✅ — 면제 전에는 항상 실패했다 |
| `gate_chain.sh` (uv run 경유) | 초기화 직후 인스턴스 | pre-commit 통과, 나머지 SKIP 크게 표시 ✅ |
| altera-rules 자기 적용 | scripts/ 전체 (ruff base·shellcheck·ast-grep) | ruff·shellcheck 클린, ast-grep 매핑 오검출 2건 지목형 면제 ✅ |

비고: `gate_chain.sh`는 테스트 실물이 없는 상태에서는 완주할 수 없다 —
첫 수용 테스트를 세운 뒤 완주 기록을 여기 남기라.
`.claude/skills/`의 심링크 스킬이 Claude Code에서 자동 노출되는지는 첫 인스턴스
세션에서 확인하라(사용자 전역 스킬에서 검증된 패턴이나 프로젝트 층 완주 기록은
아직 없다) — 확인되면 이 줄을 지우고 결과를 남기라.

### 이 실행에서 고친 결함

1. 제외 글로브 `**/target/**`가 최상위 디렉토리를 놓쳤다. fnmatch의 `*`가 구분자를 넘어 매치해 맨 앞 구획이 비면 실패한다. 디렉토리 구획 판정으로 바꾸고 회귀 검사를 붙였다(C-LOCAL-2).
2. Gradle 하위 프로젝트가 자기 빌드 파일이 없어 kafka가 모듈 6개로 뭉쳤다. 소스 세트(`src/main`, `src/test`)를 두 번째 근거로 넣어 70개가 됐다(리서치 07 실측 65개와 같은 자릿수).
3. 다이어그램이 소스 문자 상한을 넘을 때 강등이 없었다. 노드를 줄이고 사유를 남기도록 고쳤다.
4. 파이썬 데코레이터 진입점 규칙이 너무 넓어 airflow에서 13,209건이 나왔다. 테스트 소스를 빼고 패턴을 좁혀 699건이 됐다.

- SC-1.2 언어별 오라클 비교: 미실행. 오라클(javaparser, TypeScript 컴파일러 API) 반입이 남았다.
- SC-1.3 MoJoFM, SC-1.4 precision@15: 미실행. 정답 픽스처(문서화된 모듈 목록)를 아직 만들지 않았다.
- SC-1.6 가독성 사다리: 미실행. 헤드리스 렌더 측정이 남았다.

### 게이트 판정 기록 (census 오검출 심사, C-GATE-3)

- `dict-payload-return` 경고 7건은 전부 동적 키 색인이다(`load_limits`의 층 이름,
  `package_index`의 패키지 이름, `python_index`의 점 이름, `type_index`의 타입 이름,
  `_line_counts`의 경로). C-PY-1이 겨냥하는 것은 키 집합이 고정된 페이로드이고, 키가
  자료에서 나오는 색인은 이름 붙은 형태로 바꿀 수 없다. 경고로 남기고 고치지 않는다.
- `regex-on-structure` 1건은 Mermaid 식별자의 문자집합 치환이라 정규 언어다. 근거를
  적은 지목형 면제를 달았다(면제 1건, C-GATE-4의 계수 대상).
- `doc-ref-comment` 1건은 PLAN 절 번호 참조다. PLAN이 이 저장소의 정본 계획이고 절
  번호가 바뀌면 같은 커밋에서 고치는 것이 C-COMMENT-1이라 경고로 남긴다.

### SC-0.3 조율 하네스 (부분 통과)

LangGraph 1.2.11 `StateGraph` + `SqliteSaver` + SQLite 작업 저장소로 구현했다. 회귀 층에
검사 6건을 두었고 전부 통과한다(`tests/regression/test_orchestration.py`). 수용 층 승격은
사람 승인이 필요해 아침으로 미뤘다.

| 시나리오 | 상태 | 근거 |
|---|---|---|
| (a) 저널 기록 뒤 강제 종료 → 재개 | 통과 | 중복 LLM 호출 0, 누락 0 |
| (a) 저널 기록 전 강제 종료 | 통과(한계 명시) | 원격 호출과 로컬 확정은 원자적일 수 없다. 주입당 최대 1회 재호출을 계약으로 고정했다 |
| (b) 낡은 세대, 다른 소유자, 중복 제출, 없는 식별자 | 통과 | 넷 다 명시적 실패, 조용한 누락 0 |
| (c) 게이트 실패 루프 상한 2회 | 통과 | 두 번 쓰고 `exhausted`에 사유와 함께 남는다 |
| 동시 정지 5건 순서 뒤섞기 | 미실행 | 단일 프로세스 순차 임대만 시험했다. 다중 프로세스 잠금 대기는 미측정 |

이 과정에서 고친 결함: 게이트 실패로 다시 쓸 때 옛 세대의 저널 응답을 재사용해 같은
본문이 반복됐다. 저널 조회를 세대 단위로 바꿨고 회귀 검사가 그 자리를 지킨다(C-LOCAL-2).

텔레메트리는 진입점에서 `LANGSMITH_TRACING=false`와 `LANGCHAIN_TRACING_V2=false`로 끈다.

### SC-1.2 오라클 대조 (파이썬 통과, 자바 부분)

정답은 사람이 아니라 도구가 낸다(PLAN §6 3). 표본은 seed 고정 무작위다.

**파이썬, 정답은 표준 라이브러리 `ast`** (`evals/oracles/python_ast_oracle.py`)

| 대상 | 표본 | 정답 선언 | precision | recall |
|---|---|---|---|---|
| airflow, seed 42 | 30 | 216 | 1.0000 | 1.0000 |
| airflow, seed 42 | 200 | 1,492 | 1.0000 | 1.0000 |
| airflow, seed 7 | 200 | 1,884 | 1.0000 | 1.0000 |

파싱 실패로 제외된 파일 0건. SC-1.2의 파이썬 몫은 0.98 하한을 넘겼다.

**자바, 두 번째 원천은 ast-grep `outline`** (`evals/oracles/java_outline_oracle.py`).
같은 파서를 쓰므로 독립 오라클이 아니다. 독립 오라클(javaparser) 반입은 남았다.

| 대상 | 표본 | kind 룰 | outline | outline 기준 recall |
|---|---|---|---|---|
| commons-cli | 36 | 795 | 618 | 1.0000 |
| dubbo | 60 | 606 | 477 | 1.0000 |
| kafka | 60 | 1,043 | 788 | 1.0000 |

kind 룰은 outline이 내는 선언을 하나도 빠뜨리지 않았고 더 많이 낸다(kafka 표본에서
필드 225, 중첩 클래스 22, enum 4, 메서드 2, 인터페이스 1, record 1). outline이 중첩
타입과 필드를 빠뜨린다는 리서치 02와 15의 판정을 이 규모에서 재확인했다. kind 룰이
더 내는 선언이 옳은지는 독립 오라클이 판정할 몫이다.

이 대조에서 찾은 규약 차이: kind 룰은 선언자(`name = 값`)를, outline은 애노테이션과
수식어를 포함한 선언 전체를 가리킨다. 줄이 최대 1 어긋난다(commons-cli 8건, dubbo
14건). 결함이 아니라 규약 차이라 허용치 3줄을 두고 따로 센다. 인용 span의 규약은
Phase 3에서 사람이 읽을 때 정한다.

### Codex 독립 검증 1차와 그 반영 (2026-09-09 야간)

리뷰 원문은 `docs/reviews/codex-6-impl-phase1.md`. 치명 2, 중요 4, 보통 5를 받았고 전부
고쳤다. 가장 큰 것은 결정성이었다.

**치명 1. 같은 입력이 다른 사실을 냈다.** 패키지 소유자를 "먼저 본 것"으로 정해서
ast-grep 방출 순서가 모듈 엣지를 바꿨다(검증자 실측 kafka 129~164, dubbo 295~299).
고침: 매치를 정본 순서로 정렬하고(`(경로, 시작 줄, 끝 줄, message, 이름)`), 패키지와
파이썬 점 이름 색인을 소유자 집합으로 바꿨으며, 소유자가 여럿이면 참조하는 모듈이
그중에 있을 때만 해석한다. 이제 같은 입력에서 facts.json의 SHA-256이 같다(4개 레포 확인).

**치명 2. 전역 유일 조건이 되살릴 수 있는 엣지를 버렸다.** 이름이 두 번 선언되면 그
이름의 참조를 전부 버렸다(검증자 실측 kafka 15,435건 중 5,595건은 참조 모듈 안에서 유일).
고침: 색인을 다중값으로 바꾸고 해석 범위를 모듈 지역 → 저장소 전역 유일 → 거부로 두었다.

**중요.** 소유 타입 판정을 가장 안쪽으로 고정하고 소유자 없는 참조를 세기 시작했다.
다이어그램이 노드 하나로도 상한을 못 맞추면 비우고 사유를 남긴다(전에는 상한 초과를
그대로 냈다). `ref.local_type`이 엣지 표에 없어 조용히 버려지던 것을 사유별 계수로 옮겼다.
소스 읽기 실패를 줄 수 0으로 바꾸던 것을 예외로 올렸다.

**보통.** 소스 세트가 중첩되면 안쪽을 모듈 뿌리로 삼는다. 흐름의 다음 홉 선호가 뒤집혀
있어(거짓이 참보다 작아 같은 모듈을 먼저 골랐다) 교차 모듈 우선으로 고쳤다. 파이썬
데코레이터 규칙이 인자 안의 `.get(`까지 잡던 것을 호출 대상 이름만 보도록 좁혔다.

앞선 표와 견주면 타입 엣지가 늘고(dubbo 8,963 → 10,742, kafka 37,744 → 41,342) 모듈

### 남은 지적 (아침 판단 필요)

- 타입 식별자가 단순 이름이라 서로 다른 선언을 구분하지 못한다. 정규화된 이름(패키지까지)
  으로 바꾸는 것은 자료형 변경이라 사람 판단이 필요하다.
- `Module`, `Subsystem`, `FileRank`에는 근거 span이 없다. SC-1.7의 "모든 사실"에 이들이
  들어가는지는 SPEC 문면의 판정 문제다.
- SPEC의 "서드파티는 adapters 안에서만"이 PLAN §2.2의 금지 목록보다 넓다. PLAN은
  networkx와 PyYAML을 도메인 층에서 허용한다. SPEC 문면을 PLAN에 맞추는 것이 맞아 보이나
  성공 기준 변경이라 사람 승인 항목이다.
- `tests/acceptance/`는 비어 있다. SC-0과 SC-1의 수용 테스트 승격은 사람 승인 단독 커밋이다.

### Codex 독립 검증 2차의 정적 지적 반영 (같은 야간)

2차 검증이 실행 전 정적 검토에서 지적한 것을 먼저 고쳤다. `resolve_dotted(home=...)`가
공유 패키지의 임포트를 "참조하는 모듈이 소유자 중 하나"라는 이유로 자기 엣지로 흡수해
실재하는 교차 모듈 엣지를 없앴다. kafka 모듈 엣지가 159에서 109로 준 것의 상당 부분이
이 손실이었다.

고침: 임포트 해석 순서를 타입 우선으로 바꿨다. `import a.b.C`의 마지막 구획이 저장소에서
유일하게 선언된 타입이면 그 선언의 모듈이 답이고, 아니면 패키지 접두사로 찾는다. 패키지는
여러 모듈이 나눠 가질 수 있지만 타입 선언은 한 자리다.

| 레포 | 모듈 엣지(1차 반영) | 모듈 엣지(타입 우선) |
|---|---|---|
| kafka | 109 | 181 |
| dubbo | 225 | 308 |
| airflow | 517 | 519 |

kafka는 여전히 결정적이다(같은 입력 2회에서 facts 해시 동일). airflow가 거의 안 변한
것은 파이썬 임포트가 타입이 아니라 모듈을 가리켜 타입 우선 경로가 거의 쓰이지 않기
때문이다.

2차 검증의 두 번째 정적 지적(모듈 지역 해석이 import 정보 없이 같은 모듈의 동명이인을
고를 수 있다)은 아직 열려 있다. 정규화된 이름을 도입해야 닫히고, 그것은 자료형 변경이라
사람 판단이 필요하다.

### 정규화 식별자 (2차 검증의 최우선 지적 마무리)

엣지의 양 끝을 선언 파일로 식별한다(`TypeEdge.src_path`, `dst_path`). 참조도 소유 타입의
선언 파일을 함께 담는다(`Reference.owner_path`). 이름만으로는 같은 이름의 다른 타입을
구분하지 못한다는 지적을 닫는다.

L2 다이어그램의 노드 정체도 선언 파일로 바꿨다. commons-cli에서 서로 다른 `Builder`
세 개가 각각의 노드가 됐다. 전에는 한 노드로 합쳐져 실재하지 않는 관계를 그렸다.
노드 id는 짧은 자리 번호(`T0`, `T1`)이고 이름은 라벨이다. 경로를 id로 쓰면 소스 문자
예산을 다 먹는다.

같은 입력 2회 실행에서 dubbo와 kafka의 facts 해시가 동일하다. Mermaid는 dubbo 18/18,
kafka 21/21이 두 판을 통과한다.

### SC-1.3 서브시스템: 시드 안정성 측정과 그 결과로 바꾼 판정

`evals/oracles/subsystem_stability.py`로 Louvain을 시드 10개로 돌려 쌍대 ARI를 쟀다.
ARI는 표준 지표라 scikit-learn에 맡겼다(평가 전용 extra, 런타임 밖).

| 저장소 | 모듈 | 모듈 엣지 | 빌드 트리 최상위 | Louvain 군집 | 쌍대 ARI 최소 |
|---|---|---|---|---|---|
| dubbo | 84 | 308 | 16 | 11~12 | 0.9149 |
| kafka | 70 | 181 | 23 | 39~40 | 0.8211 |

kafka가 SC-1.3의 하한 0.9를 넘지 못했다. 원인을 보니 분할 규칙 자체가 틀려 있었다.
빌드 트리가 다이어그램 상한(15)보다 많은 묶음을 내면 Louvain으로 물러섰는데, Louvain은
kafka에서 39~40개를 내 오히려 묶음이 늘었고 시드마다 달라졌다. 묶음이 많은 것은 분할의
문제가 아니라 다이어그램의 문제이고 그 자리에는 가독성 사다리가 있다.

고침: 빌드 트리가 둘 이상으로 나뉘면 그것이 결론이다. Louvain은 최상위가 하나인
저장소에서만 돈다. 결과는 dubbo 16개, kafka 23개, airflow 23개이고 시드가 개입하지
않으므로 안정성은 구성상 보장된다. 이 판정으로 SC-1.3의 안정성 조건은 만족하지만,
그것은 Louvain이 안정해져서가 아니라 무작위를 쓰지 않게 됐기 때문이다.

MoJoFM은 재지 못했다. 파이썬 구현이 없고 자작은 측정 인프라 자작 금지에 걸린다
(C-LIB-1). 대안 지표(ARI, NMI)를 문서화된 모듈 목록에 대고 재는 방안은 사람 판단이
필요하다.

### SC-1.6 가독성 사다리: 미측정과 그 사유

jsdom에는 레이아웃이 없어 `mermaid.render`가 `CSSStyleSheet`와 `getBBox`에서 멈춘다.
`CSSStyleSheet`는 폴리필로 넘겼으나 `getBBox`는 텍스트 실측이라 대신할 수 없다.
리서치 13은 헤드리스 Chrome을 썼고 이 기계에는 없다. 따라서 엣지 교차 수, 라벨 잘림,
1440px 가로 스크롤은 이번 야간에 재지 못했다. 두 길이 있다. (1) Chromium을 반입해
리서치 13의 절차를 그대로 돌린다. (2) `getBBox`를 글자 수 기반 추정으로 폴리필하고
교차 수를 근사로 잰다. (2)는 값이 근사임을 표기해야 한다. 사람 판단 항목이다.

### Codex 독립 검증 3차 보고와 반영

검증자 판정은 다시 "아니오"였고, 이번에는 실증이 붙었다. 두 결함이 컸다.

**1. 임포트가 단순 이름으로 풀렸다.** `module_edges`가 정규화된 선언 대신 "저장소에서
유일한 단순 이름"을 먼저 봤다. 그 결과 `java.util.stream.Stream`이 dubbo의
`tri/stream/Stream.java`로, `org.slf4j.Logger`가 kafka의 `Log4jConfiguration.java`로
이어졌다. 검증자 계수로 dubbo 437건(교차 모듈 오답 367, 자기 엣지로 숨은 것 70),
kafka 1,508건(1,196, 312)이다.

고침: 임포트는 정규화된 선언으로만 푼다. `import a.b.C`는 패키지 `a.b`가 최상위로
선언한 `C`를 찾고, 없으면 외부 타입이라 엣지를 만들지 않는다. 와일드카드처럼 타입
이름이 없는 형태만 패키지 소유자로 찾는다.

**2. 중첩 타입이 패키지 선언처럼 취급됐다.** 내부 클래스를 패키지 수준 표에 넣어 다른
파일의 같은 이름 참조를 가로챘다(검증자 계수 kafka 314건, dubbo 32건 확정 오해석).

고침: 패키지 표에는 최상위 타입만 넣고, 같은 (패키지, 이름)을 두 파일이 주장하면 그
이름은 표에서 뺀다.

독립 대조: 정규화로 해석된 임포트에서 선언 파일의 패키지가 임포트 문자열과 다른 경우가
dubbo 0건, kafka 0건이다(전에는 이 대조 자체가 순환이라 검증자가 지적했고, 지금은
선언 파일의 실제 패키지를 본다).

알려진 참 엣지는 살아 있다: kafka `core→clients`(91), `streams→clients`(1,525),
`connect/runtime→connect/api`(299), `server→storage`(21).

### 3차 검증이 지적한 기록의 과장

- 시험 수 분류가 틀렸다. 커밋 `30812f4` 기준으로 단위 38(그래프 22, 구조 8, 심볼 8),
  회귀 9(조율 7, 룰 2)로 합계 47이다. "단위 41, 회귀 6+2"는 틀렸다.
- 같은 범위 소유 모호성은 거부되지만 출력에서는 `no_owner`와 구분되지 않는다.
  "모호를 보고한다"는 서술은 아직 참이 아니다.
- 흐름 깊이 검사는 `len(hops) <= 4`만 보므로 홉이 0이어도 통과한다. 깊이를 고정했다는
  서술은 과장이다.
- 명시 임포트 일치 지표는 같은 자료로 판단하고 같은 자료로 검사해 순환이었다.
- 게이트 전 단계 통과는 이 기계에서만 확인했고 검증자 환경에서는 재현되지 않았다
  (임시 디렉토리 권한).
